# Bangumi 定制设计系统：整合实施路线图 v0.1

- 状态：**提案，待审核后执行**。
- 目标：将已确认的改版方向、目标 Tokens 与组件/页面组合规范，渐进式整合到 `bangumi-frontend`，最终形成可维护的全站统一视觉系统。
- 依据：[改版方向](01-改版方向-v0.1.md)、[目标 Design Tokens](02-目标-Design-Tokens-v0.1.md)、[基础组件规范](03-基础组件规范-v0.1.md)、[条目详情页组合规范](04-条目详情页组合规范-v0.1.md)，以及对 `bangumi-frontend` 当前实现的代码审查。
- 首个试点：动画条目概览 `/subject/:id`，以 [SHIROBAKO 首页审计](../审计/条目/首页-SHIROBAKO.md) 为代表。

## 1. 结论与实施原则

当前前端已具备 React、Panda CSS 和共享 `@bangumi/design` 组件库，但新系统尚未成为视觉的唯一来源：现有页面、共享组件与全局壳层仍分别携带历史色值、尺寸和响应式规则。因此不能采用“逐页润色”方式；它会让同一语义继续在各页面漂移。

本路线采用以下单向链路：

```text
审计与设计决策
  -> 语义 Tokens 与主题
  -> 基础组件的可访问契约
  -> 内容模式与页面组合
  -> 条目详情页试点
  -> 按页面族推广
  -> 视觉回归、旧规则退场
```

### 1.1 不变的原则

1. **渐进替换，不改变已验证的信息架构与核心任务路径。** 资料、讨论、收藏和编辑的内容顺序不因视觉升级而重组。
2. **先建立唯一的样式来源，再迁移页面。** 新页面和被改动组件不得继续新增裸色值、裸字号、任意阴影或孤立断点。
3. **高密度内容优先。** 连续列表、定义列表、数据行、讨论串和正文流是一等模式；Card 仅用于确有独立边界的对象。
4. **主题、响应式和状态同步设计。** 亮/暗主题、375/768/1280/1600px 宽度，以及键盘和加载/错误/禁用状态均是同一交付物。
5. **保留兼容层，但为其设退出条件。** 迁移期间可保留 `bgm-*` class 作为旧页面钩子；一个页面族完成验证后，移除已替代的局部覆盖和历史样式。

## 2. 当前实施基线

| 领域         | 已有基础                                                                               | 整合缺口                                                                   | 结论                                               |
| ------------ | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | -------------------------------------------------- |
| 样式基础设施 | Panda CSS 已扫描 website、design 与 icons 源码；生成产物已纳入仓库。                   | 配置尚未表达目标文档中的原始/语义 token、主题或设计断点。                  | 先落地 token 层，不能直接翻修页面。                |
| 共享组件     | `@bangumi/design` 已包含 Link、Button、Input、Section、Tab、Pagination、Topic 等组件。 | 多个组件直接承载历史颜色、尺寸和圆角；部分页面再以选择器覆盖组件默认样式。 | 将现有组件视为迁移入口，不视为已完成的新设计系统。 |
| 页面壳层     | Header、Footer、PageContainer 已广泛复用。                                             | 容器宽度、边距、字体、导航和移动行为仍是局部规则。                         | Shell 与容器是最高杠杆的第一波改造对象。           |
| 条目页       | 已有封面、资料、收藏、评分、角色轨、关联、评论、讨论、吐槽及行为测试。                 | 布局和视觉仍以旧值拼装，窄屏仅在局部断点退化，基础组件存在覆盖。           | 适合作为端到端试点，保持数据和业务逻辑不动。       |
| 主题与排印   | 目标规范已定义亮/暗语义色、系统字体栈与 CJK/西文规则。                                 | 当前全局样式和组件尚未消费这些规则，深色模式没有页面级实现。               | 主题与字体必须从试点第一天进入实现和测试。         |
| 登录态业务   | 前端已有收藏、进度、编辑和发布功能样本。                                               | 设计审计未覆盖完整的权限、错误、撤销、提交和通知状态。                     | 不为未审计流程臆造完整状态机，先进行定向审计。     |

## 3. 先完成的决策与审计

在更改共享组件前，确认以下设计决策。它们会影响全站，不应由单个页面实现临时决定。

| 决策          | 当前提案                                                                     | 需要确认的原因                               |
| ------------- | ---------------------------------------------------------------------------- | -------------------------------------------- |
| 当前导航/页签 | 主文本保持正常对比度，使用 2px 品牌粉指示线或有限填充，并有 `aria-current`。 | 决定主导航、条目导航、筛选和分页的共同语言。 |
| 主按钮密度    | 默认视觉高度 40–42px；紧凑工具栏 32px；触屏命中面积至少 44px。               | 影响收藏、发布、筛选、编辑与 Header。        |
| 小屏资料轨    | 首屏显示 4–6 条关键信息，其余同页可逆展开。                                  | 决定条目页的阅读节奏和信息完整性。           |
| 宽屏条目布局  | ≥1600px 使用资料轨 + 阅读列 + 辅助轨；阅读列不超过 720px。                   | 保证宽屏提升比较效率而非制造空白或超长行。   |

同时补齐以下证据，产出截图、任务路径和状态矩阵，而非直接出视觉稿：

1. 登录、注册、找回和验证码。
2. 收藏、评分、进度修改、撤销和失败反馈。
3. Wiki 编辑、发帖、回复、草稿、校验错误与权限不足。
4. 通知、菜单、弹层、删除/危险操作、空/加载/局部失败状态。
5. 375px、480px、768px 与中等桌面宽度的真实操作行为。

## 4. 工作包 A：Tokens、主题与全局基础

### 4.1 目标

将 [02-目标 Design Tokens](02-目标-Design-Tokens-v0.1.md) 映射为 Panda 可消费的原始 token 与语义 token，并以根属性支持亮/暗主题。业务组件只使用语义 token，不能知道当前处于哪种主题。

### 4.2 实施范围

1. 在 `panda.config.ts` 定义：品牌与中性色阶、`bg-*`、`text-*`、`border-*`、`color-link`、状态色、字体、字号/行高、空间、尺寸、圆角、阴影、断点和动效。
2. 将亮/暗色值放在主题语义层；设置稳定的根属性约定，例如 `data-theme='light' | 'dark'`。
3. 在应用入口统一引入系统字体栈、数值排印、基础背景/文字色和减少动态效果规则；`textarea`、Input 和编辑器应继承同一 CJK/西文字体策略。
4. 为媒体、代码编辑器等确有运行时颜色的区域定义边界；业务语法色可例外，但普通 UI 不得以例外为由继续硬编码。
5. 运行 Panda codegen/cssgen，审查并提交生成产物；CI 用生成结果差异阻止遗漏。

### 4.3 完成标准

- 亮/暗主题切换不改变组件结构或业务逻辑。
- 正文、链接、品牌填充、焦点环、错误与禁用在两主题均满足规范对比度。
- 新增 UI 不出现未登记的颜色、字号、圆角、阴影和断点。
- 以中文、日文、英文、长数字、长用户名和长标题验证字体回退、换行与行高。

## 5. 工作包 B：基础组件与内容模式

### 5.1 优先顺序

| 批次 | 组件/模式                                                                | 目的                                                           |
| ---- | ------------------------------------------------------------------------ | -------------------------------------------------------------- |
| B1   | `AppShell`、`PageContainer`、Typography、Link、Divider                   | 统一页面画布、阅读宽度、文本层级、链接语义与分隔节奏。         |
| B2   | Button、Input、Textarea、Select、Checkbox、Radio、Form、Message/Toast    | 建立可访问的操作和反馈基础，为登录态与编辑流程预留契约。       |
| B3   | 主导航、section navigation、Tabs、Pagination、Menu/Popover               | 明确“路由跳转”与“同页切换”的边界，并解决当前态/焦点/溢出行为。 |
| B4   | Continuous List、Definition List、Meta Row、Section heading、Cover media | 将 Bangumi 的高密度资料与社区阅读结构提炼为可复用模式。        |
| B5   | Topic、评论、回复、评分、媒体轨                                          | 保留各社区内容的阅读差异，不强制合并成统一评论卡片。           |

### 5.2 组件契约要求

每个共享组件必须记录并通过 Storybook/测试验证：

- 目的与禁止使用场景；
- 语义 HTML 与键盘行为；
- 结构槽位、有限变体和 token 引用；
- default、hover、focus-visible、active、disabled、loading、error 等适用状态；
- 窄屏、触屏命中面积、文本溢出和长 CJK 内容的规则；
- 亮/暗主题和可访问性要求。

迁移期间优先保持原有公开 props 和 DOM 语义，以内部 recipe 或静态 Panda class 替换样式。需要改变 API 的组件，新增明确的 vNext 变体并逐调用点迁移，不用无语义的 `color`、`shape` 组合扩张旧 API。

## 6. 工作包 C：条目详情页试点

### 6.1 边界

试点只重构页面组合、展示和交互反馈；保留现有数据请求、路由、收藏、进度更新和测试 fixture。未完成登录态审计前，`action-area` 仅预留位置，不重设计完整收藏/评分业务规则。

### 6.2 建议结构

```text
Global masthead
Subject title band
Subject context navigation
  IdentityRail        封面 + 定义列表事实
  SummaryColumn       标题、简介、标签、关键入口
  RatingRail          评分、人数、排名、分布摘要
  ActionArea          已审计动作或登录态预留
MediaRail             角色与制作人员
RelationList          关联条目与推荐
ReviewPreview         长评摘要
TopicList             讨论主题
CommentList           吐槽/短评
Footer
```

### 6.3 响应式规则

| 视图        | 组合规则                                                                                         |
| ----------- | ------------------------------------------------------------------------------------------------ |
| 375–767px   | 单列优先；封面与核心事实可短暂并列，完整信息可逆展开；评分仅保留总分、人数和排名，分布按需展开。 |
| 768–1023px  | 封面/资料与摘要可双列；评分下移至摘要后；不硬缩放为三列。                                        |
| 1024–1599px | 恢复资料轨，评分依可用宽度位于摘要旁或下方。                                                     |
| ≥1600px     | 允许资料轨、主阅读列、评分/辅助轨并列；正文列保持可读行长。                                      |

角色横向轨是有意的内容例外：保留水平滚动，但要提供下一项截断提示、触摸与键盘可达性，焦点进入时使项目最小幅度滚入可视区。

### 6.4 试点验收

1. 交付 375、768、1280、1600px 的亮/暗主题可运行页面或等价设计稿。
2. 使用真实长标题、日文原名、长元数据、长用户名、空状态和局部失败状态。
3. 关键路径可通过键盘完成；焦点环、展开控件、导航、横向轨均可见且可理解。
4. 页面无意外横向滚动；横向媒体轨等例外有明确可发现性。
5. 保留并扩充条目页既有行为测试；新增语义、状态和响应式视觉回归。

## 7. 工作包 D：按页面族推广

禁止按随机页面推进。每一波先完成该页面族共享的内容模式与状态，再开始下一个页面族。

| 波次 | 页面范围                                  | 主要复用能力                            | 进入条件                         |
| ---- | ----------------------------------------- | --------------------------------------- | -------------------------------- |
| D1   | Header、Footer、搜索、条目详情及条目子页  | Shell、容器、导航、资料行、媒体、分页   | C 试点通过。                     |
| D2   | 目录、发现、收藏列表、人物/角色           | 连续列表、封面媒体、筛选、定义列表      | B4 稳定，条目页媒体/列表已验证。 |
| D3   | 小组、讨论、日志、时间线                  | 社区阅读模式、回复层级、作者/时间元信息 | Topic/评论模式与编辑态约束明确。 |
| D4   | 登录、收藏评分、Wiki 编辑、发帖回复、通知 | 表单、业务反馈、权限与危险操作          | 定向审计完成，业务状态机经确认。 |

每波按以下固定步骤执行：

1. 为页面族建立“旧规则 -> 新模式”的迁移表，列出不可改变的任务与信息顺序。
2. 在共享层补齐缺失模式，并写 Storybook 与组件测试。
3. 改造一个代表页面，完成主题、响应式、键盘和视觉验证。
4. 将同一模式推广到该页面族其他页面。
5. 删除已被替代的局部覆盖、历史 class 和重复硬编码；记录例外及其到期条件。

## 8. 工程分工与目录约定

| 产物                        | 建议位置                                         | 责任                                           |
| --------------------------- | ------------------------------------------------ | ---------------------------------------------- |
| 原始/语义 token、主题、断点 | `bangumi-frontend/panda.config.ts`               | 前端实现，依据 `02`；设计系统审核语义命名。    |
| 生成样式系统                | `bangumi-frontend/packages/styled-system`        | Panda 自动生成，必须提交，不手工编辑。         |
| 可跨页面复用组件            | `bangumi-frontend/packages/design/components`    | 组件实现、Storybook、单元测试。                |
| 页面组合和业务适配          | `bangumi-frontend/packages/website/src`          | 页面团队；不得将通用视觉规则回写为局部硬编码。 |
| 规范、审计、决策记录        | `bangumi-design/设计系统`、`bangumi-design/审计` | 设计系统文档为需求和验收依据。                 |

建议每周进行一次短审：确认 token/组件新增项、已迁移页面、遗留覆盖数、视觉回归结果和待决策项。任何新增的共享视觉能力都必须明确归属；不能确定归属时，先留在页面层并记录原因，不仓促泛化。

## 9. 质量门槛与退出条件

### 9.1 每个 PR

- 只引入已存在的语义 token，或同时提交经过审核的新 token。
- 修改共享组件时更新 Storybook、单元测试和受影响页面的视觉基线。
- 运行相关行为测试、Panda 生成、lint、类型检查、格式检查和构建。
- UI 改动至少覆盖对应的桌面与窄屏视图；交互改动覆盖键盘焦点与非 hover 反馈。

### 9.2 每个页面族

- 亮/暗主题均无明显层级、对比度或媒体显示问题。
- 375/768/1280/1600px 无页面级横向滚动，或已记录且符合组件契约的例外。
- 无新增历史色值和无归属的局部样式；迁移范围内的旧覆盖已删除。
- 真实 CJK/西文、长文本和空/加载/失败状态已审查。

### 9.3 全站完成定义

当所有页面族均完成迁移并满足质量门槛时，才可视为“全站风格统一”。完成不以视觉相似为唯一标准，而以以下事实判断：

1. 语义 token 是页面视觉值的唯一常规来源。
2. 同一语义的链接、当前态、输入、危险操作和反馈在全站有一致行为。
3. 全站 Shell、页面容器、排印、亮/暗主题、响应式与无障碍基线一致。
4. 剩余 legacy hook 均有明确的兼容理由和移除计划。
