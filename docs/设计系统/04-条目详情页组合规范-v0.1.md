# Bangumi 定制设计系统：条目详情页组合规范 v0.1（提案）

- 状态：**提案，待审核**。
- 试点路由：动画条目概览，以 [SHIROBAKO 首页审计](../审计/条目/首页-SHIROBAKO.md) 为代表样本。
- 依赖：[改版方向](01-改版方向-v0.1.md)、[目标 Tokens](02-目标-Design-Tokens-v0.1.md)、[基础组件](03-基础组件规范-v0.1.md)。
- 目标：定义可复用的“条目详情页”页面组合规则；不重新定义条目数据模型、收藏/评分业务规则或未审计的登录态动作。

## 1. 页面要解决的任务

条目详情不是营销落地页。用户应能在同一页面中：识别条目、判断评分与基本事实、阅读简介、浏览人物和关联关系，并自然进入章节、评论、讨论、吐槽或个人记录。

因此页面优先级为：

1. **定位与判断**：名称、媒介类型、封面、状态/评分、最关键的事实和简介。
2. **理解与浏览**：标签、人物、关联条目、分布/排名等可帮助判断的资料。
3. **参与与延伸**：章节、评论、讨论、吐槽，以及登录后才出现的收藏、评分、编辑动作。

页面仍保持连续阅读流。评分、标签、人物和社区内容是资料的不同维度，不拆成争夺注意力的大卡片。

## 2. 信息架构与区块顺序

### 2.1 默认顺序

```text
Masthead
条目标题带（名称 / 媒介类型）
条目上下文导航（概览、章节、角色、讨论……）
┌─ 主要资料区 ────────────────────────────────────────┐
│ 封面 + 条目事实轨 │ 摘要与标签 │ 评分与排名（桌面） │
└──────────────────────────────────────────────────┘
人物与制作人员
关联条目
长评摘要
讨论主题
吐槽/短评
分页或延伸入口（按区块需要）
全站页脚
```

- 此顺序延续现有页面已验证的阅读路径：资料在前、关系内容在中、社区内容在后。
- 不新增无证据的推荐 Banner、自动轮播、浮动 CTA 或跨区块“立即评分”广告。
- 每个区块都有可读的标题、稳定锚点和适当的“查看全部”链接；不要求用户滚回顶部才能进入子路由。

### 2.2 条目上下文导航

`概览 / 章节 / 角色 / 讨论 / 评论 / 吐槽` 等是可独立访问的路由，使用 `section-nav` 链接而非 ARIA Tabs。

- 当前项使用 `aria-current="page"`、主文本色和 2px 品牌粉指示线；不只改变为粉色文字。
- 桌面端置于标题带之后；移动端仍在标题之后，过长时单行横向滚动，保持当前项可见。
- 导航在滚动时是否粘性：**v0.1 建议仅桌面端粘性**，且不遮挡锚点标题；移动端先保持普通文档流，待试点验证后决定。

## 3. 桌面布局

### 3.1 容器与栅格

| 视图        | 容器                             | 栅格规则                                                                       |
| ----------- | -------------------------------- | ------------------------------------------------------------------------------ |
| 1024–1279px | `container-content`，最大 1200px | 资料区可为 `260px + minmax(0, 1fr)` 两列；评分移至摘要后或右上角的第二行。     |
| 1280–1599px | `container-content`，最大 1200px | `260px` 事实轨 + 主内容；评分与摘要在主内容中以可用宽度决定并列或纵向。        |
| ≥1600px     | `container-wide`，最大 1440px    | 允许 `280px` 事实轨 + 主阅读列 + `272px` 评分/辅助轨；长文阅读列不超过 720px。 |

这与旧页“292px 信息轨 + 约 875px 主区”的高密度优势兼容，但将固定像素布局改为可伸缩列，避免宽屏只扩展空白、也避免中等屏幕被挤出横向滚动。

### 3.2 主要资料区

| 区域             | 内容                                          | 布局与视觉规则                                                                                           |
| ---------------- | --------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `identity-rail`  | 封面、别名、放送/发售、原作、制作、站点等事实 | 封面置顶；下方为定义列表。标签为 `text-secondary`，值为 `text-body-sm`。不要以独立阴影卡片包裹整条轨道。 |
| `summary-column` | 条目名、类型、摘要、标签、少量关键入口        | 摘要为 `text-body`，长文本控制在阅读列宽度内；标签使用浅色信息面，不升级成营销标签云。                   |
| `rating-rail`    | 分数、排名、人数、评分分布                    | 数值优先于装饰；可用 `bg-subtle` 分组，但不使用大圆角和浮夸图表。窄宽度时移到摘要之后。                  |

**封面规则：** 默认保持原图比例，使用 `radius-sm`；不得裁切成圆角头像。未加载时使用与封面比例一致的占位，避免资料区跳动。

**事实轨规则：** 事实按领域分组（名称/制作、播出、链接等），极长内容可换行；不为了保持两列把日文原名、长 URL 或制作名单强行截断。

**首屏紧凑模块标题：** `章节列表`/`曲目列表`、`大家将…标注为` 和 `收藏盒` 分别是任务区标题、信息面内的上下文说明和操作面板标题，均使用 `text-label`。它们需要可扫描的 14px/20px/500 文字，但不升级为阅读流中的 `text-section-title`；后者只用于角色、关联、评论、讨论和吐槽等独立内容分区。

### 3.3 分区与社区内容

- 桌面端区块之间使用 `space-6`，区块内部使用 `space-3` 至 `space-4`；不以每区一个 Card 产生视觉断裂。
- 分区标题使用 `text-section-title`，可在右侧放置低强调“更多”链接；带头像、摘要或作者信息的独立文章标题使用 `text-title-sm`。链接目标必须说明内容，例如“查看全部 48 个讨论”。
- 人物区可使用横向媒体轨，但必须显示可继续浏览的提示，并支持触摸、滚轮/拖动（如实现）和键盘；不可假设用户发现横向滚动。
- 关联条目优先使用封面 + 文本的紧凑连续列表或网格。网格是内容媒体密度的变体，不是 Card 系统。
- 长评摘要、讨论、吐槽按各自阅读结构渲染：长评强调标题与摘要，讨论强调主题/最后回复，吐槽强调作者与短文本。不得强行用同一“评论卡片”统一它们。

### 3.4 间距所有权与 Subject Detail 映射

条目详情采用“外部由页面组合拥有、内部由组件拥有”的间距模型。无视觉表面的 section 是连续信息流的一部分，不应在自身根节点设置 `margin-bottom` 或透明 padding；其外部节奏由最近的 section stack 提供。

| Subject Detail 场景                | 间距所有者                        | 推荐角色                                      | 实现方式                                                 | 组件自身可以保留的空间                                                        |
| ---------------------------------- | --------------------------------- | --------------------------------------------- | -------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 页面画布到内容                     | `PageContainer`                   | `layout.gutter`                               | 容器 `padding-inline`，按断点变化                        | 无                                                                            |
| 事实轨、主内容、评分/辅助轨三栏    | `columns` / `primaryColumns`      | `layout.section`                              | grid `column-gap`                                        | 各列不得再加模拟列距的横向 padding/margin                                     |
| 左侧信息框、目录、最近收藏         | `columnLeft`                      | `layout.group`                                | `display: flex; flex-direction: column; gap`             | 信息框的封面与定义列表、列表行内部节奏                                        |
| 评分收藏面板、分享工具             | `columnRight`                     | `layout.group`                                | `display: flex; flex-direction: column; gap`             | 有边框/背景的收藏面板可保留 `component-panel-padding`；分享工具仅保留行内 gap |
| 章节、简介、标签这组首屏资料       | `SubjectPrimaryBlocks` 的 stack   | `layout.group`                                | 子 section 作为 stack 的兄弟元素                         | 标签浅色表面的 `padding`，章节行和标签项的内部 gap                            |
| 人物、关联、推荐、评论、讨论、吐槽 | `SubjectSecondaryBlocks` 的 stack | `layout.section`                              | 子 section 作为 stack 的兄弟元素                         | 各自列表的行内 padding、媒体轨的 gap、表格单元格 padding                      |
| Section 标题与正文/更多链接        | `SubjectSection`                  | `layout.group` 或 `layout.compact`            | header/body 的内部 gap；header 内标题与链接使用 flex gap | 标题行的必要对齐 padding，不再用 `margin-bottom` 作为通用区块距离             |
| 连续列表行                         | 列表项                            | `component.list.rowBlock` 与 `layout.compact` | 行自身的 block padding，内部 flex gap                    | 分隔线、交互热区、单元格 padding                                              |
| 封面/角色横向轨                    | 媒体轨容器                        | `layout.group`                                | flex/grid gap 与滚动容器必要的 inline padding            | 封面标题与元数据的紧凑垂直节奏                                                |
| 面板标题、正文、表单字段           | 面板本身                          | `component-panel-padding`、`layout.group`     | 有背景/边框的 surface 使用 padding；字段组用 gap         | 不可把面板 padding 作为与相邻面板的距离                                       |

事实轨中的 Wiki infobox 使用语义 `<dl>`：每一行以 `dt` 表示字段名、`dd` 表示可含多个链接的字段值。默认采用 `text-body-sm`、`component.list.rowBlockDense` 和相邻行间的 `component.list.divider`；字段名和值保持内联，避免窄侧轨上的长字段名挤压值或制造僵硬双列。

#### 对当前试点的迁移准则

1. 将 `SubjectPrimaryBlocks`、`SubjectSecondaryBlocks`、`columnLeft`、`columnRight` 改为明确的 stack 容器，分别拥有其子区块的外部 gap。
2. 移除 `SubjectSection`、`IndexSidePanel`、`CollectSidePanel`、`CollectionPanel` 根节点上只为相邻面板留白而存在的 `margin-bottom`。这些组件仍可保留内部边框、标题内距、列表行内距和带表面面板的内容 padding。
3. `SubjectSection` 的默认样式只表达 section 的内部结构与分隔线；标题与正文作为其直接子项，由 section 的 `layout.compact` gap 分隔，不使用 header margin。不要让不同 section 通过覆盖其 `margin`、`padding` 来争夺页面节奏。首屏中的章节、简介、标签可通过 stack 的角色变体变紧凑，而不是由每个 section 各自改写外边距。
4. 保留已属内部结构的值：列表行上下 padding、标签背景的 padding、收藏面板正文 padding、图标与文字 gap、表格单元格 padding。这些值服务于可读性、边框和命中区，不与父级 gap 重复。标题下的连续列表或表格首项不再添加 top padding，避免和 header/body gap 叠加；末项保留 bottom padding 以维持区块的收束节奏。
5. Section 标题与右侧“更多”链接只使用 header 的 `gap` 分隔，标题本身不加模拟间距的右 padding。连续数据表的单元格可保留列间 gutter，但首列左缘与末列右缘必须和 section 内容边缘对齐；行分隔使用 `component.list.divider`。

## 4. 响应式重排

### 4.1 768px 以下：单列阅读优先

```text
标题与条目导航
封面 + 名称/类型 + 核心事实（并列，空间不足时纵向）
评分摘要（分数、人数、排名）
简介
标签
完整事实信息（可折叠分组）
人物、关联、长评、讨论、吐槽
```

- 页面横向内距遵循 token：16px；正文保持 14px，不用缩小文字换取列数。
- 封面与关键信息可并列，但封面不小于可辨识的最小展示尺寸；空间不足时改为纵向。
- 评分分布图可在 375px 宽度隐藏为“查看评分分布”展开项；总分、人数和排名不可隐藏。
- 信息轨移入简介之后，默认展示最关键 4–6 条事实；其余以“展开完整信息”显示。展开是同页可逆操作，必须保留状态和可访问名称。
- 人物横向轨继续存在时，首项与截断下一项应给予可浏览暗示；若实现成本或可用性不佳，改为两列紧凑列表，而非强行缩小头像。

### 4.2 768–1023px：过渡双列

- 允许封面/事实轨与摘要并列；评分置于摘要下方。
- 关联条目可增加列数，但内容标题、封面和元信息仍需有足够宽度。
- 不使用桌面三列硬缩放；侧轨的功能优先级低于简介与主内容阅读。

### 4.3 1024px 以上：资料并列、阅读不变宽

- 恢复事实轨；评分根据可用宽度在摘要旁或摘要下。
- 宽屏增加关系信息与评分的并列空间，不能把摘要、长评或讨论正文拉到难读的超长行。
- 现有条目页的横向人物轨不是全站默认布局；仅人物数量与媒体资料密度确有价值时保留。

## 5. 状态、交互与无障碍

### 5.1 页面状态

| 状态               | 规则                                                                                                                |
| ------------------ | ------------------------------------------------------------------------------------------------------------------- |
| loading            | 标题、封面、事实、摘要和评分使用接近最终尺寸的 skeleton；社区区块可渐进加载，但不得导致用户已经阅读的内容大幅跳动。 |
| partial failure    | 某一资料源/评分图加载失败时，保留其他内容并给出局部、可理解的错误与重试；不将整页置空。                             |
| unavailable / 受限 | 对不存在、权限不足或成人内容限制，提供明确原因和安全返回路径；不只给状态码或空白。                                  |
| empty community    | 评论、讨论或吐槽为空时，说明没有内容；登录后才可创建的操作须说明登录要求，不假装当前用户可操作。                    |

### 5.2 键盘与语义

- 页面只保留一个 H1（条目名）；主要区块用有层级的 H2，区块内子结构使用 H3。
- 跳过链接应使键盘用户直接进入主内容；条目导航、横向媒体轨、所有“展开”控件和“更多”链接均可聚焦。
- 封面替代文本采用“《条目名》封面”；纯装饰图片使用空 alt。评分图需有文本化的评分分布摘要。
- 横向轨若可滚动，须避免焦点被裁到不可见区域；键盘进入某项时自动最小幅度滚动使其完整可见。
- 颜色主题切换不应改变信息顺序或交互位置。

### 5.3 登录态预留

收藏、评分、进度、编辑与发表入口在登录后出现，但 v0.1 尚未有实测状态机。页面仅预留 `action-area` 位置：

- 桌面：标题/评分附近的低干扰操作组，不挤压摘要阅读列。
- 移动：位于核心资料后、社区区块前；不使用遮挡内容的永久悬浮条。
- 具体动作、权限、错误、撤销和成功反馈，须在登录态审计后定义为业务组件。

## 6. 亮/暗主题规则

- 页面画布、信息面、分隔线、文字、链接与评分图均引用语义 token；不能通过将亮色页整体反色实现深色模式。
- 封面、用户头像等媒体在深色背景上保留其原始内容色彩；必要时只为媒体容器增加 `border-subtle`，不叠加黑色滤镜。
- 品牌粉用于当前导航指示、主要操作与有限选中态；评分、警告、危险和链接维持各自语义色，防止深色主题中所有强调混成同一粉色。
- 两套主题以同一页面结构和字号交付；不得为深色主题另做更低信息密度版本。

## 7. 试点交付与验收

### 7.1 最小交付物

1. 1280px 桌面、1600px 宽屏、768px 平板、375px 手机的亮/暗主题设计稿或可运行页面。
2. 主要资料区、人物/关联、长评、讨论、吐槽各至少一个真实内容样本；包含长标题、日文原名、长元数据和空状态。
3. 键盘焦点顺序与导航/展开/横向轨的交互原型。
4. 关键颜色对比度与图片加载前后布局稳定性的检查记录。

### 7.2 验收问题

1. 用户能否在首屏快速找到名称、封面、评分、简介与进入下一条目子路由的路径？
2. 小屏是否能读完核心资料与社区内容，而无需页面级横向滚动？
3. 用户是否能区分条目资料、关系内容和三种社区内容，且不把它们误认为同一种卡片？
4. 宽屏增加的列是否确实支持比较与资料扫描，而没有让阅读行宽失控？
5. 深色主题是否在不降低层级和链接可发现性的前提下完成相同任务？
